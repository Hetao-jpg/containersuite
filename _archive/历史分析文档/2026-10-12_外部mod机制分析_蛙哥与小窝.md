## 1. 已实施（T1–T5）

### T1 单调钟节流 —— `Shared/PollThrottle.cs`
- **为什么值钱**：`DateTime.UtcNow` 差值在系统时钟**回拨**时（改时间 / 大跨度 NTP 校正 / 虚拟机休眠恢复）会让 `(now-last)` 变负 ⇒ 所有 `Elapsed < N 秒` 判据**恒真** ⇒ 闸门卡死且全程无声。典型后果：`LogOnce` 3 秒窗恒真（**连异常告警都被静音**）、单拖 0.4s/0.5s 闸门（松手没反应）、读档 1.5s 闸门（恢复被永久忽略）、prefs 2s（配置永不落盘）、`_prepareCache`(0.2s)（升级长期被判"不能升"）。
- **做法**：`Environment.TickCount64`（单调、64 位不回绕、与帧率无关）。`NowMs` / `ElapsedMs(since)` / `Due(ms)` / `Reset()`。
- **命名避让**：小窝叫 `RuntimePollGate`，我们叫 `PollThrottle`；节流字段统一 `*Gate` 后缀；不改任何既有函数名/键名。
- **迁移 14 处**：DIY 的 `_lastTargetConsume`/`_lastEndDragProcessed`/`_lastPrefsFlush`/`_lastLogTimeByKey`/`_lastReapplyFromMetaTime`/`_prepareCache`/`_ggiCache`/`_resizableCache`/手柄自检、SBE 无、CI 的读档闸门、`SkipXiaowoBayRestore._lastSweep`、`SaveSlotScope` 槽号缓存。
- **边界**：`ResizeDiag` / R1 探针里的 DateTime 冷却仍在，但整体在 `#if DIAG` 内（`Restore.cs 356-390`、`ResizeDiag.cs 27-177`）⇒ **Release 产物已无 DateTime 节流点**。
- ⚠️ 编号避让：2026-10-07 的 `CacheLimits.Trim` 调用注释里也叫 "A1"，与本批无关；本批统一 `T*`。

### T2 每帧每容器升级闸门 —— `_upgradeStampCache` + `TryConsumeUpgradeStamp`
- **诚实定性**：这是**保险 + 观测点**，不是修已知 bug。今天只有两处会真扣料（单拖 `EndDragPatch`、组拖协程），而组拖以 `yield` 开头、天然不与单拖同帧 ⇒ 结构上不该被触发。
- **与蛙哥的差异（有意）**：① 蛙哥 `_lastUpgradeFrame` **永不清理**（裸指针键无限增长）——我们不抄，本字段已登记 `CacheRegistry`（场景/读档都清）；② 蛙哥闸门放在扣料**之前**，我们放在 `PrepareUpgradeInternal` **成功之后** ⇒ 被拦下的必然是"本该真升的一次"，留痕是真信号而非误报。
- **组拖侧刻意不挂**：跨帧风险（材料已被别的入口销毁、地址被复用）由 B-3' 的 uniqueId 双验兜住，帧闸门帮不上忙。理由写在 `GroupDrag.cs` 循环体里。
- 字段名以 `Cache` 结尾是有意的：将来若恢复 `_shared` 的 R6 门禁，它天然在判定范围内。

### T3 组拖「事件丢失」对账 —— `ReconcileGroupDragArm()`
- 判据：已武装 + 鼠标抬起**连续 5 帧**却没等到 `EndGroupDrag` ⇒ 无条件 Warn 一条"本次批量升级不会发生"。
- 为什么不是单帧：MelonLoader 的 `OnUpdate` 可能排在游戏派发 `EndGroupDrag` **之前**，单帧会对每次正常结束的组拖误报。
- **只观测、不自动复位**：擅自清 `_groupDragArmed` 会与游戏自身状态打架（也不知道该不该替它把材料放回去）。先拿证据，再决定要不要干预。
- 已知误报面：若游戏支持非鼠标框选（键盘/手柄），会误报；误报只多一行日志。
- 未武装时方法第一行返回 ⇒ 常态零开销。

### T4 页ID旁路文件按「局」隔离
- **问题**：`SaveBagPaging.ids` 只按 `saveSlotId`（**槽号**）分行。同一槽开新游戏时槽号不变、物品 uniqueId 重排 ⇒ 上一局页归属被当成这一局 ⇒ 第二页物品整片叠进第一页（与 A-2 修的"跨档 uid 复用"同类，但这份在磁盘上，不会被读档清缓存救回）。
- **做法（最小、向后兼容）**：行格式 `<slot>#<runKey>;pageCount;ids...`；`runKey` 取 `PlayerStore.runID`（清洗为 `[0-9A-Za-z_-]`、截断 24 字符）；**无 runKey 段的老行照旧匹配**（升级套件本身不让玩家已有数据失效，下次存档就地升级格式）；本行 runKey 与当前局不符 ⇒ 只跳过**这一行**并告警一次（绝不删其它槽的行）；拿不到 runID ⇒ 不写该列 = 不做隔离（旧行为）。
- **实现时踩到并修掉的坑**（值得记）：`SaveIdSets` 的"替换旧行"原本自己 `int.TryParse(表头)` —— 写成 `<slot>#<runKey>` 后它认不出旧行 ⇒ 每次存档**追加**一行、读侧永远命中靠前的旧行 ⇒ **页归属直接冻结**。已把表头解析抽成唯一的 `TryParseSlotHead`（读/写共用），并用离线脚本复刻验证 5 种情形 + "就地替换不追加"。

### T5 `SyncModifiedState` 收尾同步 —— DIAG 实验（默认关）
- **事实**：蛙哥在批量升级收尾（`BatchDragUpgrade.cs:215`）与骰子吸收后（`DestinyDice.cs:898`）都调 `GameItem.SyncModifiedState()`；**本套件全树零调用**。语义只从签名可知（`void SyncModifiedState()`），未反汇编原生实现。
- **做法**：DIAG 专属 cfg `27_SyncModifiedStateProbe`（默认 false，带中文标签）→ 成功升级收尾补调一次，成功走 Diag 留痕、**抛异常走无条件 Warn**（异常正是要看的结论）。
- **证据**：Release 全量重建后产物 DLL 里 `grep SyncModifiedState` 与 `27_SyncModifiedStateProbe` 均 **0 命中**。
- **后续**：实验表明需要 → 去掉 `#if DIAG` 转正；不需要 → 连同 cfg 项一起删（不留"看起来在生效"的死代码）。

## 2. 评估后**不**采纳的（含理由）

### 2.1 蛙哥的延迟销毁队列（`_pendingDestroy` + 每帧 `FlushPendingDestroy`）
它解决的问题真实（不在游戏枚举集合的过程中 `Destroy`）。**但我们不适合**：
1. 队列要跨帧持有 `GameItem` **对象** ⇒ 违反本项目 R4 硬规矩（禁止跨帧持 IL2CPP 包装器）；
2. 会引入"已消耗但仍被枚举到"的窗口 —— 我们的组拖本来就有 6 帧间隔，期间那堆 `unitCount=0` 的材料还在容器里，可能被自己的 `MatchCategory` 再收一次；
3. 我们**没有**"当场销毁出问题"的证据（`ConsumeMaterial` 一直这么跑），不该凭想象加机制。

### 2.2 小窝 `FinishDrag` 的 `[MethodImpl(NoInlining | NoOptimization)]`
它压住的是"带 EH + 一串 IL2CPP 包装器调用"的方法体，与本项目 S8u-3e 的教训同源。我们的对策是"方法体拆小 + 启动期预热"，目前没有哪条收尾方法在复发该问题 ⇒ **暂无对象可加**。原则：只在真出过问题的具体方法上加，不全量撒（全量损性能且掩盖问题）。

### 2.3 小窝的"轮询启动拖拽 + `IsTopmostWindowHit`"
- 小窝的手柄命中是 `RectTransformUtility.RectangleContainsScreenPoint`：**纯几何、不走 raycast、也不看 `activeInHierarchy`**；`IsTopmostWindowHit`（唯一用 raycast 处）只是补 z-order。
- **我们不能抄轮询起拖**：那正是"两套同时改形状"的根源。我们的拖拽起点走 Unity 事件 ⇒ 事件分发天然保证最上层独得 ⇒ **不需要** `IsTopmostWindowHit`。这个取舍是对的，别退回去。
- 我们的轮询入口只做光标反馈（`Resizer.Cursor.Tick`），不启动拖拽 —— 与它明确分工。

### 2.4 其它明确别抄
| 项 | 为什么 |
|---|---|
| 蛙哥 `Finalizer` 两个分支都 `return null` | 吞掉原方法异常 = 把故障藏起来。我们原样 `return __exception` |
| 蛙哥快照存 `GameItem` 跨 Prefix→Postfix | 同帧才安全；我们组拖跨帧，必须"指针 + uid"（B-3'） |
| 蛙哥目标只用 `hoverItem` 单判据 | 悬停容器网格空白处就完全不武装；我们两级判据（hoverItem → hoverInventory→owner）更稳 |
| 蛙哥 `_lastUpgradeFrame` 不清理 | 裸指针键永久累积 |
| 蛙哥 `ConsumeOne` 的 `catch → Destroy()` | 兜底把**整堆材料**销毁（`SetUnitCount` 失败时更糟） |
| 蛙哥全量无条件日志（每次组拖必打一行） | 我们已确立"结果无条件、细节走开关" |

## 3. 源级核验结论（与现有防线直接相关）

1. **我们拦批量路径的两个 Patch 是唯一拦截点** —— 蛙哥的批量 Postfix **直接调用**
   `ContainerUpgradeV2.ConsumeNutsDirectly` 与 `LuckScoutBackpackUpgrade.DoUpgrade`
   （不经任何 `Prefix_*` 游戏钩子）⇒ `SkipWageUpgradeRestore` 里那两个 Patch
   "不能删"由源码证实。且它被拦时 `num2++`（记失败、**不扣料**）⇒ 材料留给我们的协程 ✓。
2. **B-3' 的"地址复用"有明确对手行程** —— 蛙哥在 `EndGroupDrag` 的 **Postfix（同帧）**
   扣料并销毁材料，我们的组拖协程**下一帧**才动；那正是"刚释放的地址最可能被复用"的时刻。
   没有 uid 校验时 `IdFieldNull` 会通过（新对象有合法 identifier）⇒ 吞错材料。
3. **小窝手柄"熄火式"能生效的真正机理** —— `IsAlive` = `handles==8 && LiveHandleCount==8`，
   而 `LiveHandleCount` 只数 `rectTransform != null`、**不看 `activeInHierarchy`** ⇒
   `SetActive(false)` 不会让它重建；反过来**销毁**手柄会让 `LiveHandleCount<8` ⇒
   下次 `Attach` 重建 8 个（这正是早年"清它建它"打架 + `DestroyHandles` 冷方法深栈首 JIT 崩溃的原因）。
   ★ 我们代码里"熄火后**退出 raycast**"的注释**表述不准**：小窝手柄命中是纯几何判定，与 raycast 无关；
   真正封死它的是同一段代码里的 `States.Remove`。**若将来有人把 `States.Remove` 简化掉、只留 `SetActive(false)`，小窝照样能拖。**

## 4. 机制要点（压缩留存，以后排查还会用到）

### 4.1 蛙哥「选多物品升级容器」= `BatchDragUpgrade`（257 行）
- 入口与我们同目标 `ItemMultiSelectHandler.EndGroupDrag`，但是 **Prefix 快照 + Postfix 同帧同步执行 + Finalizer 清状态**。
- 目标 = `__instance.hoverItem`（单判据）；待吸收 = `selectedItems` 按 **`Pointer` 相等**剔除目标。
- 4 类目标分派：命运之骰 / 妙妙箱（`ConsumeNutsDirectly`）/ 虚空珠（`DoUpgrade(..., applyShape:false)`，循环末尾**一次** `ApplyBeadShape`）/ 瓶子打印机。
- 逐件 `try/catch` + 成功/失败计数，**单件失败不中断**（我们目前是"业务性失败即 break"，异常也 break —— 见 §5）。
- 容器升级有**两个独立触发点**（`PrefixTarget_WageBox` / `PrefixMayHaveValidInventorySlot_WageBox`），靠 `ConsumedThisFrame(ptr)` 保证同帧只扣一次。
- 触发判据 `IsDragRelease()` = `ItemMouseDragHandler.current != null && IsDraggingItem && !Input.GetMouseButton(0)`（"游戏认为在拖、鼠标已松"）——3 个模块各抄一份。
- 段位持久化双通道：tag（`wb_stage`）+ `WageSaveStore`（`Mods/WagesPerks/wages_data_<runID>.txt`，带 `#runID=`/`#saved=`/`#storeVersion=1` 头，`LOAD_DELAY_FRAMES=30`，位置键 = 库存标识 + 槽号）。

### 4.2 小窝「手柄拖拽」= `ContainerWindowResizer`（1855 行，我们 DIY 的移植来源）
- `States: Dictionary<IntPtr, ResizeState>` 键 = **contentWindow 指针**；`VisibleStates` + `StaleStates`（先收集、循环后统一 Destroy+Remove）。
- **双入口**：① Unity 事件路径（`PrepareDrag` 里 `data.useDragThreshold = false`，让 1px 位移就能起拖）② 轮询路径（每帧 `Tick` → 几何命中 → `GetMouseButtonDown` → `BeginPointerDrag`，之后每帧自己 `DragAtPointer`）；`Drag(PointerEventData)` 首行 `if (_pointerDrag) return true`，事件路径让位给轮询。
- 多窗口仲裁：`isActive` 优先，其次比 `GetSiblingIndex()`；起点前先排除关闭按钮。
- 拖拽数学：`_columnPixels = max(1, inv.widthPixels / cols)`；像素增量取整成列/行 → `TryResizeGridWindow` → 用**实际（clamp 后）**尺寸差 + pivot 修 `anchoredPosition`。收尾 `RememberWindowSize` + `RememberGridShape` + `FixBounds`。
- **窗口每次重新可见都会 `TryRestoreRememberedGridShape` + `BringHandlesToFront`**（它抢回尺寸主权的动作，也是我们必须在"重新可见"路径上赢下来的原因）。
- 可见性用 250ms 节流；不可见/失焦时 `Deactivate()` 主动中止拖拽。
- 我们比它强的地方（别退回）：S8r 空转跳过（鼠标没动 + 无拖拽 + 上帧无 hover ⇒ 整帧跳过，6 帧强制一次）；不用轮询起拖。

## 5. 未验证 / 待实机

- T1：系统时钟回拨是低概率场景 —— 改动是**语义等价**的替换，收益是"消除一整类静默失效"，但没有实机复现过旧行为。
- T2：闸门"不该被触发"。实机跑一次单拖 + 一次组拖，日志**不该**出现"同一帧内第二个入口"。
- T3：对账行**不该**出现。若出现 → 说明组拖事件确实会被吃掉，届时再决定是否加复位。
- T4：`PlayerStore.runID` 的**取值时机**（是否读档完成前为空）未实测 —— 若在早期为空，则那段时间不做隔离（退化为旧行为，安全）。`saveSlotId 相同但 runID 不同` 的同槽新游戏场景未实机复现。
- T5：`SyncModifiedState()` 的真实语义（未反汇编原生实现）；需在 DIAG 构建里打开开关实测。
- 蛙哥"先扣料 → 我们下一帧读到已释放指针"的竞争是否真实发生（需实机日志；B-3' 已按最坏情况防御）。
- 蛙哥逐件不中断 vs 我们"业务性失败即 break" —— 是否要把"异常"与"业务性失败"分开处理（异常 continue + 留痕，业务性 break），**待定**，不在本批。
- 小窝 `TreeNodeRender` 手柄节点的渲染细节（只看了锚点/sizeDelta 参数）。
