一、四个工程
================================================================================

  ★ 2026-10-06：4 个 DLL 合并成 1 个（见下方“为什么合并成 1 个 DLL”）。
    源码仍留在原 4 个目录里（文件一个没动，命名空间也没动），
    由 ContainerSuite.Infrastructure.csproj 的 <Compile Include> 拉进来编译；
    另外 3 个 csproj 已改名 *.csproj.disabled，不再单独产出。

  ContainerSuite.Shared
    产物:     并入 CustomInfrastructure.dll
    命名空间: ContainerSuite.Shared
    角色:     共享库。不是 Mod，没有 MelonInfo。

  ContainerSuite.Infrastructure
    产物:     CustomInfrastructure.dll   ← 唯一产物
    命名空间: CustomInfrastructure
    角色:     唯一的 MelonMod 入口。转发生命周期、挂三家的补丁

  ContainerSuite.SaveBag
    产物:     并入 CustomInfrastructure.dll
    命名空间: SaveBagExpand
    角色:     仓库扩容 + 主仓库分页 + 滚轮

  ContainerSuite.DIYUpgrade
    产物:     并入 CustomInfrastructure.dll
    命名空间: DIYUpgrade
    角色:     拖材料升级容器 + 拖边缘缩放 + 读档恢复

  为什么合并成 1 个 DLL（2026-10-06）:
    早先的判断是“合到一个程序集要排除 4 份 AssemblyInfo.cs（CS0579）+ 改构建链，
    收益只是少 3 个文件”，所以暂不合并。复核后真实收益不止于此：
      ① 消除“缺 1 个 DLL → 套件全崩”的部署故障面（旧版第二节 ④ 明确记载过）；
      ② 消除 4 处 AssemblyVersion 同步漂移（check-suite-version.ps1 的存在就是证据）；
      ③ 玩家升级只覆盖 1 个文件，不会出现 4 个版本错配；
      ④ 构建从 4 次 MSBuild 收敛成 1 次。
    代价 = 必须连带做完三件事，少一件就出回归：
      B3  4 份 AssemblyInfo.cs 合并成 1 份（否则编译期 CS0579 重复特性）；
      B1  mod.cs / DiyUpgradeMod.Core.cs 的“按程序集扫补丁”改成按命名空间过滤
          （否则同一目标被两个 Harmony ID 各装一遍，Postfix 跑两遍、
           Patch 计数虚高，日志里的 15 个 / 7 个 / 13 个全乱）；
      B2  3 个 MelonPreferences 段并成 1 个 [CustomInfrastructure]
          （ModManager 归属规则只看 DLL 文件名，见 ManagerState.CategoryBelongsToMod；
           不改的话 41 个配置项里有 31 个会从面板里消失）。
      旧段 [SaveBagExpand] / [DIYUpgrade] / [自定义容器升级] 的值由
      DiyUpgrade.CfgMigration 一次性自动搬家，用户配置不丢。

  分工（互不重叠，别打破）:
    · trashcan 垃圾桶 / dossier 档案箱 / cassette_player 磁带播放器   ->  基础设施
    · SaveBag 主仓库 / ShowcaseInvSaveBag 展示柜 / HiddenInvSaveBag 海报暗格
      / BackInvSaveBag 柜台 / FrontInv 客户柜台                        ->  扩容仓库
    · 箱子 / 背包 / 笼子 / 多槽 / 机器模组槽 / Wage 容器              ->  容器升级

二、安装与部署
================================================================================

  构建:
    cd "D:\games\open code work"
    dotnet build ContainerSuite.sln -c Release

    ⚠ 构建带三道守卫（CommonMod.props 各 Exec 一个脚本，只在编译
      ContainerSuite.Infrastructure 时跑一次，任一失败 = MSB3073 构建失败，
      所以 pack.ps1 走构建时打包前必过）：
      · P4  check-suite-version.ps1    SuiteVersion.cs 与 AssemblyInfo.cs
                                        的版本号必须一致 → 改版本号要改 2 处
                                        （合并前是 5 处），只改一处会编不过。
      · DOC check-readme-defaults.ps1  README「默认尺寸」表必须等于
                                        SaveBagExpandConfig.CreateEntry 的默认值。
      · FBD check-forbidden.ps1        禁止事项 #21（Validate 不许带实参）
                                        + #22（网格重操作文件必须引用
                                        WorldReadyGate 或在 $allowGate 登记）。
      ★ ContainerSuite.Infrastructure\AssemblyInfo.cs 是全工作区唯一允许写
        [assembly: ...] 特性的地方（2026-10-06 合并后只剩这一份，另外三份已
        改名 .disabled，再加回来会 CS0579）。文件是 UTF-8 无 BOM，编辑器直接改。

  产物（只有 1 个）:
    ContainerSuite.Infrastructure\bin\Release\CustomInfrastructure.dll

  部署:
    把 CustomInfrastructure.dll 复制到 <游戏目录>\Mods\（同名旧文件直接覆盖）。
    ★ 升级时要**先删掉** Mods\ 里残留的旧版 SaveBagExpand.dll / DIYUpgrade.dll /
      ContainerSuite.Shared.dll —— 它们已经没有消费者了，留着只会让人以为版本没换。

  ⚠ 部署前必须关闭游戏，否则 DLL 被占用报 Device or resource busy。
  ⚠ Release / Debug 产物字节数常常相同，不能靠文件大小判断是否部署成功，
    看修改时间或 sha256。稳妥做法是逐个 md5sum 对比源与目标。
  ⚠ 换机器 / 换游戏目录: 只改 _shared\CommonMod.props 里的 <GamePath>，
    或 dotnet build -p:GamePath="..."，不用动源码。

  部署后自查（启动游戏看日志，三行都要对上）:
    ① ContainerSuite v1.7.3（... / 容器升级 v1.7.3 / ...）  ← 版本号
    ② 已避让 XIAOWOTradePerks (7/7)                            ← 7 不是 6
       ⚠ 若显示 (6/7) 或"有方法没挂上"，说明 S8n 的手柄补丁没挂上，
         会退化成两套手柄叠加（手柄判定不明确）。
    ③ 已清理 XIAOWO 残留拖拽手柄 N 个                        ← 首次启动可能出现
       N=0 属正常（没升级过就不产生手柄）。N>0 是历史遗留被清掉了。
    ④ 缺席时看这几行：日志里完全没有 ① 的横幅 = DLL 没进 Mods\ 或加载抛
       FileNotFoundException / TypeLoadException，看 Latest.log 头几行。
       合并后只剩 1 个 DLL，已经不存在“4 个缺 1 个”这种故障了。

  一键打包脚本（推荐）:
    工作区根目录有 pack.ps1 + pack.bat。
    · 双击 pack.bat  ->  自动编译 + 复制 CustomInfrastructure.dll + 打包 zip

      dist\ContainerSuite-v1.7.3\
      dist\ContainerSuite-v1.7.3.zip

  回滚:

    阶段名。回滚 = 挑一个标签的目录，把里面的 DLL 覆盖回 Mods\：
    （2026-10-06 之后的备份里只有 CustomInfrastructure.dll 一个；更早的备份里

================================================================================
三、配置与热键
================================================================================

  配置在 UserData\MelonPreferences.cfg，三段分类名是硬编码的，与 Mod 显示名无关
  （改 MelonInfo 显示名不会丢配置）。

  ⚠ 段名必须与 DLL 文件名一致 -- ModManager（Nico's Lab）把 cfg 段落归属到 mod
    的规则是 Normalize(段名) == Normalize(DLL 文件名去掉扩展名) 或 ==
    Normalize(MelonInfo 名)。段名对不上，那个 mod 的配置项在 ModManager 面板里
    一项都不显示（2026-10-02 踩过：DIY 段名是中文，面板里空了）。
    因此本套件三段名 = CustomInfrastructure / SaveBagExpand / DIYUpgrade。

  分类（cfg 段名）:

    CustomInfrastructure
      归属: 基础设施
      内容: 各容器目标宽高（只扩不缩）

    SaveBagExpand
      归属: 扩容仓库
      内容: 6 个容器尺寸（主仓库 / 展示柜 / 海报暗格 / 柜台 / 客户柜台）、
            【仓库·扩容】启用、【主仓库·分页】启用与页数、滚轮、
            诊断 DiagLog

    DIYUpg    DIYUpgrade
      归属: 容器升级
      内容: 升级材料（垃圾/废金属/金属锭）、升级键、拖拽缩放开关、各类上限、
            诊断日志 DiagLog、读档尺寸恢复 RestoreOnLoad、
            避让热开关 SkipXiaoBay / SkipWageBox / SkipVoidBead（S8k/S8l 新增）。
      段名 2026-10-02 由 自定义容器升级 改来（ModManager 按段名匹配 DLL
      才能显示配置项），旧值自动迁移。

    ★ 避让热开关（S8k/S8l 新增，首次运行自动写入 cfg，默认全开）:

      SkipXiaoBay   = true   避让·精工扩舱（XIAOWO）
      SkipWageBox   = true   避让·蛙哥妙妙箱（WagesPerks）
      SkipVoidBead  = true   避让·蛙哥虚空珠（WagesPerks）

      语义 = 「关掉则把该容器的尺寸主权交还给对方 mod」。
      默认全开 = DIY 全权优先。

      ★ 三个开关语义**不一样**，别当成一样的东西：
        · SkipXiaoBay / SkipWageBox：纯避让。关掉无害，对方照常玩。
        · SkipVoidBead：**移交门**，不是纯避让。保持开启 = 蛙哥原版
          「拖垃圾逐格解锁」正常玩；玩家按住升级键拖材料 = 自动永久移交 DIY。
          ★ 别关它 —— 虚空珠的材料（junk）两边重叠，关掉 = 两边都抢同一格材料。

      ★ 实现是「补丁常驻 + 判据函数第一行短路」，**不做 Unpatch / 不重装**
        （IL2CPP 上动态重生成 detour 会 Internal CLR error 0x80131506），
        所以同一帧生效、不需要重启游戏。
      ★ 读取失败会 fallback 到"保持避让"（= 现状行为），
        绝不因为配置读不到就静默改变主权。

  默认值（S8g 起，新玩家开箱即用）:

    ExpandEnabled         = true    （仓库扩容总开关）
    SaveBagPagingEnabled  = true    （主仓库分页）
    ScrollEnabled         = true    （滚轮滚动）

    老玩家的 cfg 里已有旧值，MelonPreferences 沿用旧值，不受影响。

  热键 / 输入:

    LeftAlt + 把材料拖到容器上
      升级容器（材料键可配，默认金属锭）

    拖窗口边缘
      调整容器尺寸（7 个手柄；未升级过 spent=0 时硬拦截）

    TAB
      主仓库切页（分页开启且页数 > 1 时）

    鼠标滚轮
      在容器窗口上滚动查看

4.1 基础设施（CustomInfrastructure）
--------------------------------------------------------------------------------

  · 只扩大不缩小: 生效尺寸 = Max(当前值, 配置值)
  · 三个补丁入口: GameItem.ValidateShapeState / PixelWindow.Show() /
    PlayerStore.LoadGame

  🔴 读档崩溃防线:
     LoadGamePostfix 一进读档立即置 _suppressUntilFrameEnd，30 帧后延迟恢复
     协程在 finally 里解锁。原因: ValidateShapeState 在读档深栈
     （LoadGame → DecodeSaveItem → Expel）里跑 JIT 重路径会触发 CLR fatal
     0x80131506，托管 catch 抓不到、日志无堆栈。
     finally 解锁不可省，否则本 mod 的 Postfix 永久静默（表现为"改了配置不生效"）。

4.2 扩容仓库（SaveBagExpand）
--------------------------------------------------------------------------------

  默认尺寸:
    主仓库 24×10、展示柜 9×7、海报暗格 4×4、柜台 18×4、客户柜台 18×4。
    与 SaveBagExpandConfig.cs 的 CreateEntry 默认值一一对应
    （check-readme-defaults.ps1 每次编译 Infrastructure 时自动核对，不一致直接构建失败）。

  S8f 起:

        移交不可逆：否则松开键就掉回蛙哥，两边来回抖。
        想彻底断掉移交可能（排查冲突）才把 `SkipVoidBead` 设为 false
        = 无条件归 DIY（S8j 旧行为）。

      ★ **S8j→S8l 的教训**：S8j 把虚空珠设成"无条件接管"是为了消除
        "两边都用 junk"的材料重叠，但**过度接管**——蛙哥原版逐格解锁
        （1~200 格）被完全掐死，窗口标题退回游戏本体的"虚空珠 储物区"
        （蛙哥 4 处 titleString 一次都没跑到），实机截图确认。
        **消除冲突 ≠ 剥夺对方全部玩法**。正确姿势是"设移交门"：
        默认对方全权，用玩家意图（按键）作为移交信号。

      ★ 移交判据**必须无副作用**：`VoidBeadHandoverRequested` 只读键+tag，
        **绝不写 tag**。判据链每帧被调几十次，在里面写 tag 会让判据无法推理，
        且与 `HandOverVoidBead` 两处写同一 tag 容易打架。
        真正的移交动作统一在 `ItemMouseDragHandler.EndDrag` 里执行 ——
        那是唯一能同时拿到 dragSource 和 dragTarget 的时机。
        `HandOverVoidBead` **幂等**（已移交直接 return），
        否则玩家第二次按键会把已升到的 16x16 当成新基准，白升一级。

      ★ `MigrateLegacyVoidBead` 必须跟着移交门收紧。
        S8j 时它无条件迁移（配套无条件接管）；S8l 若还不收紧，
        玩家没移交它就先打了基准 + 调 RegisterVoidBeadGrid，
        而 GetWageCategory 仍返回 None → DIY 认都不认却已动过它的数据。

      ★ `Prefix_DoUpgrade` 判据从 `HasDiyMigrated` 换成 `VoidBeadHandedOver`。
        两者不等价：前者只表示"基准记过"，可能出现在任何容器上；
        "该不该拦蛙哥"真正要看的是**主权有没有移交**。

      ★ 加开关时必须覆盖该模块的**每一个** Prefix 入口。蛙哥侧原有两套判据：
        6 个走统一判据 OwnsWageBox，另有 5 个历史遗留走窄判据 HasDiyMigrated，
        只改前者会漏掉后者 → 开关关掉后出现"避让关了但恢复链还在拦"的半开状态。

      ★ 排障时看这两行基本日志（**F11/F12 台账已于 S8m 移除**）：
        · 「Wage 避让：N/N 成功」—— N<N 说明有补丁没挂上（静默失效）
        · 「虚空珠已移交给 DIY：基准 20x10」—— 移交门触发记录
        详细诊断用 cfg 里的 `DiagLog` 开关（默认关，不占配置行）。

     S8n 一度准备方案 2（拦 XIAOWO 那 4 个覆写 widthPixels 的 Postfix），

  ★ 9. IL2CPP 硬约束（这几条踩过很多次）
     · 热开关只短路判据函数第一行，绝不 Unpatch / 重装（会
       Internal CLR error 0x80131506）。
     · `ref` 参数签名必须用 `ilspycmd --ilcode` 核对，普通反编译会丢

   13. 不要相信 "HarmonyPriority 高就能拦住别的 Mod 的 Prefix"

    S8n 实测（2026-10-02）：DIY 的 MayTarget Prefix 加了
    [HarmonyPriority(900)]，同一目标方法上蛙哥的 Prefix（默认
    Priority）仍然照常执行，几十次日志都出现。Harmony 的
    "任一 Prefix 返回 false 则短路后续" 在多 Mod 场景下不总是成立。

    → 要拦别的 Mod，**只能 patch 它自己的方法**（我们 patch
      Prefix_WageBox_Target 用 return false 拦住），
      或 **给它的方法加前置补丁**，不能指望 Priority 顺序。

   14. 不要用"入口层已封"推断"对方全套都停了"

    S8n 血坑（2026-10-02）：S8i 把 XIAOWO 的升级入口封死后报了"6/6 已挂载"，
    但 XIAOWO 还有一套**独立的拖拽手柄** ContainerWindowResizer（8 个手柄），
    跟本 mod 的 7 个叠在同一窗口上抢鼠标 —— 两套会同时改形状。
    玩家看到的症状是"手柄判定不明确 + 网格残留"，
    而日志显示避让全部成功，**极具误导性**。

    → 排查兼容冲突时，除了看补丁挂没挂上，还要 `grep` 对方有没有
      自己的 `Tick()` / `Update()` / UI 交互子系统。入口封死
      不代表 UI 不会自己动。S8n 已加 Prefix_Attach 封它。

   15. 不要拦对方方法的"内部实现层"

    已在 S8i 定论并在 S8n 复现：XIAOWO.TryUpgradeBay 写的是
    `if (!ApplyStoredShape(target) || !ItemsMatch(...)) throw ...`
    —— 把 ApplyStoredShape 拦成 false 会逼它自爆、回滚并报错。
    同理 ApplyWindowSize 里那 4 个覆写宽高属性的 Postfix
    （BayExpansionFixedWindowWidth/Height 等）也不要随便拦，
    它们是 XIAOWO 自己 ApplyWindowSize 期间的必要配套。

    → 拦的层次从外到内：入口（TryHandleIngot 等）→ 收敛点
      （TryRestoreRememberedGridShape、Attach）→ 内部实现层（别碰）。

   16. 不要把对方私有状态表抄一份

    S8n 做上限对齐时，如果抄 XIAOWO 的 LegacyShapes 字典，
    它改表我们不会知道 → 静默地越来越不一致，且没有报错。
    正确做法是反射调它自己的 `TryGetUnlockedShape`（internal static）。
    同理优先**逐容器**对齐，不要动玩家的全局 cfg（6 个 bay 满级形状
    各不相同，压全局 BoxMaxW 会让所有箱子上限一起缩水）。

   17. 不要在"每帧被调几万次的 getter"上挂方向未验证的拦截

    S8n 曾计划方案 2：拦 XIAOWO 那 4 个覆写 `widthPixels` 的 Postfix。
    实机证明方案 1+3 就够了，方案 2 作废。但结论值得留着：

    · 那 4 个 Postfix 的真实挂点是 `GameGridInventory.widthPixels` /
      `PixelWindow.widthPixels`（不是 childWidth —— 我最初按方法名猜错了）。
      这两个是 **get/set 的真实存储属性**，覆写 = 直接改网格像素宽。
    · 真要拦，该拦更外层的 `ApplyWindowSize`（收敛点），
      而不是它内部的属性 getter。
    · 先加只读日志确认它**还触不触发**（门控字段是否非零），拿到数据
      再动手。核桃的工作方法那条"新功能第一次失败就做可观测实验台"，
      在这条上同样适用 —— 尤其当拦截点在每帧路径上时。

   18. HarmonyPatch 的目标方法要从 IL 里解出来，不要按方法名猜

    `ilspycmd` 反编译里显示 `/*Could not decode attribute arguments.*/` 时，
    真实目标被编码在特性字节里。解法：导出 `--ilcode`，从
    `.custom instance void HarmonyLib.HarmonyPatch::.ctor(...)` 那段
    hex 字节里解出 UTF-8 字符串。
    S8n 就是靠这个发现"实际是 widthPixels 而不是我以为的 childWidth"。
	
   19. 不要按源码目录名推断对方 DLL 的内部命名空间

    S8o 血坑（2026-10-04）：WagesPerks.dll 的源码目录是
    `D:/games/mod调试/蛙哥/JacksonPerks/`，源码里的 namespace 也是
    `JacksonPerks`，但**部署的 DLL 内部命名空间是 `WagePerks`**。
    DIY 侧的 14 个避让补丁失效了好几天（启动日志一直报"未检测到
    JacksonPerks.*"），但 cfg 里 24 项 Wage 配置项却已生成 —— 两条检测
    路径不一样：`WageContainerRegistry.ShouldCreateWageEntries` 走目录
    扫描（找含 "Wage" 的文件名），`SkipWageUpgradeRestore.Install` 走
    `TypeCache.FindTypeCached("JacksonPerks.*")`。

    → 核对方类型一律以 `ilspycmd -l class <dll>` 的实际输出为准。
      源码目录名、源码里的 namespace、MelonInfo 名、DLL 文件名，这四个
      可以两两不同。

   20. 不要在只剩一套手柄时还保留"与对方对齐上限"的逻辑

    S8o 血坑（2026-10-04）：S8n 引入的 `ClampToXiaowoCeiling` 把 DIY 拖拽
    上限夹到 XIAOWO 满级形状，目的是"消除两个 mod 各自 clamp 到自己的上限
    时的边界抖动"。但 S8n 同时把 XIAOWO 的手柄拦掉了 —— **抖动的前提
    已经不存在，上限对齐变成纯负担**，引入两个反向 bug：
      · 恢复路径（读档 / Show）经过 TryGetGridShapeLimits 时被夹回
        XIAOWO 满级（smuggler_bay 从 13x13 → 10x10）；
      · 拖拽路径一旦形状到 XIAOWO 上限（10x10），上限被夹死，永远出不去。

    → 引入"与对方对齐"类逻辑前，先问：**对齐的前提（双方都有手柄）
      是否还成立？** 若对方入口已被本 mod 封死，对齐只是给自己添乱。
    → TryGetGridShapeLimits 被拖拽 / 恢复 / tooltip **三处**调用，
      任何在此处的上限夹取都要考虑三条路径的语义差异。

   21. 不要把 EmporiumEntry.Validate() 改成 Validate(true)

    S8t 血坑（2026-10-05）：EmporiumEntry.Validate(bool) 的 bool 参数
    语义是"是否强制重建 Emporium 布局"。传 true 会重排**所有**容器窗口
    的 anchoredPosition / pivot，把主仓库等窗口拉回游戏原版位置 ——
    破坏"上端固定在原版位置、往下溢出屏幕"的期望行为。

    核桃实机截图报"主仓库窗口下端完整显示在屏幕里"，与 02:19 工作区
    备份逐方法对照，定位到两处实参被改动：
      · EmporiumEntryStartPatch.ApplyAllResize 末尾
      · EmporiumEntryStartPatch.RefreshAllVisuals 末尾
    两处原本都是 `Validate()` 无参。

    → 正确写法：`Validate()` 无参（= Validate(false)），只做轻量状态
      校验，不动布局位置。

    → 通用规则：调 API 前先明确它改什么、不改什么。
        · SetAllDirty / ForceRebuildLayoutImmediate —— 只标脏不改位置
        · Validate(true) / 带 "rebuild"/"relayout" 语义的 API —— 会重排
      凡是"布局重建类"的调用，加进容器套件前都要确认副作用。
      与禁止事项 #9（不要手写 rectTransform.sizeDelta）属于同一大类。
22. 不要在加载期（WorldReadyGate.ShouldDefer == true）对
       GameGridInventory 执行 SetShape / Expel / UncheckedAccept /
       ForceRecomputeDynamicBackground 等操作

    S8u 血坑（2026-10-05）：SaveBagExpand 的分页绑定在加载期走了
    ClearGrid → Expel → UncheckedAccept 全链路，此时 DIYUpgrade 和
    CustomInfrastructure 已对 GameGridInventory 的宽高属性下了
    Harmony 补丁，MonoMod 在深栈中再次 CompileMethodHook 直接触发
    Internal CLR error 0x80131506（托管 catch 抓不到，日志无堆栈）。

    → 所有会对网格做“增删物品 / 改形状 / 强制重算背景”的代码，必须
      先检查 WorldReadyGate.ShouldDefer，加载期一律 return 或入队。
    → 分页、升级、恢复、拖拽缩放四类操作全部适用。
    → 与禁止事项 #6（不要给带 ref bool __result 的方法打 Prefix）同源：
      都是 IL2CPP + MonoMod 在加载深栈下的 JIT 冲突，宁可推迟到帧末，
      不要抢在加载期执行重活儿。
