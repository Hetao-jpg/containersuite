给接手这份代码库的 AI 的推荐阅读指南
你拿到的是一个经过数月高频救火、单点维护的 IL2CPP mod 工程。它功能完整、防御周到，但代码注释已经积累到淹没代码的程度。这份文档不是一份"该删什么"的清单——而是一套让你自己发现问题、自己判断取舍的方法。请把它当作一个资深同事的推荐，不是命令。

一、先建立一个直觉
在打开任何文件之前，先记住一个反直觉但重要的事实：

代码里的注释，其价值衰减速度远快于代码本身。

代码每次重构都会自动暴露编译错误；注释不会。所以：

三年前的注释，今天可能已经在说谎

三周前的"临时说明"，今天可能已经成为噪音

"决策依据"越写越多，但重复的决策依据不产生新信息

你的目标不是"删注释"，而是让代码本身重新成为可读的、可信的、可维护的文本。

二、识别信号：什么时候一段注释值得怀疑
打开任意文件，扫一遍，对这些模式敏感：

信号 1：注释里出现日期 + 代号
text
【2026-10-07 更正】
S8u-3e 取证结论
C-1（2026-10-12）
A-2（2026-10-12）：...
值得问自己：这条信息对"现在读代码的人"有用吗？如果它只在描述过去某次决策的背景，那它更像是开发日志——而开发日志的归属应该是 git commit，不是代码。

信号 2：注释自我否定
csharp
// 【2026-10-07 更正】原注释称「DIYUpgrade 也 Postfix 了同一个方法
//    —— 该说法在**合并后的当前代码里已不成立**...
值得问自己：如果原文已经不成立，那这段"更正"是给谁看的？是给已经读过旧注释的人看的——但那是越来越少的一群人。将来读代码的人只看到"更正过"，看不到"原来说的是什么"。

信号 3：注释描述已删除的代码
csharp
// ── 【S8i】Target 家族入口 —— ★ 2026-10-12（C-1）已整段删除 ──────────
//   历史：S8i 曾在这里 patch 蛙哥自己的 3 个入口 Prefix
//   加回时请按 ilspycmd --ilcode 从 WagesPerks.dll 读出的签名重建...
值得问自己：这段注释的唯一价值是"如果加回来怎么做"——而这一点完全可以靠 git log -S "PrefixMayTarget_WageBox" 恢复。注释在做的，是给 git 打替补。

信号 4：注释比代码长
拿一个方法看：/// <summary> 有 8 行，方法体 3 行。

值得问自己：为什么一个 3 行的实现需要 8 行的说明？通常是因为"为什么这么做"很长——那这部分内容就不属于这里。

信号 5：try/catch 里塞着长注释
大量这样的结构：

csharp
try { ... }
catch (System.Exception ex) { CatchLogOnce.Warn("...", ex); }
// 注释解释为什么要 catch
值得问自己：如果每个 catch 都配一段解释，那这套工程的"异常哲学"就应该抽到一个 docs 文件里，而不是散在 200 个 catch 旁边。

三、分类框架：五问定去留
对每一段怀疑的注释，问自己五个问题：

明天它消失，谁会受损？

没有具体的人 → 删

"未来的维护者"→ 看第 2 问

"玩家"（比如注释在警告某个行为不能改）→ 保留

这条信息能在别处拿到吗？

git log 能查到 → 删（前提：commit message 写得好）

已有 docs 覆盖 → 删，改成一行 docs 链接

只能在这里说明 → 继续第 3 问

它会过期吗？

会（比如涉及具体游戏版本、具体偏移值）→ 这种信息不该在代码里，因为代码不会过期检查

不会（比如"这个函数必须是叶子方法"是编译期/运行期契约）→ 保留

后人看到这行，会不会"顺手改坏"？

会（比如"这里故意不打 [JitWarmup]"）→ 必须保留，且加粗提示

不会 → 继续第 5 问

它是在解释"是什么"还是"为什么"？

"是什么"（API 用法）→ 精简到一句话

"为什么"（设计约束）→ 进 docs/design/

四、主动发现问题的练习
不只是被动扫描，可以主动做几个实验——这些实验会自己暴露问题。

实验 1：盲读一个文件
随便挑一个 DiyUpgradeMod.*.cs，先跳过所有注释，只读代码。问自己：

我能看懂这段逻辑在做什么吗？

我要花多久？

如果答案是"看不懂"或"花很久"——那说明注释没有在帮代码变清晰，只是在补充信息。这个文件的注释就值得重审。

实验 2：git log 一条注释里的日期
挑一段带日期的注释，比如 【2026-10-12 T4】：

bash
git log --since="2026-10-11" --until="2026-10-13" --oneline
如果能看到对应的 commit，且 commit message 里已经包含了注释说的事——那注释就是重复信息，可以删。

实验 3：git blame 一段可疑的注释
bash
git blame -L <行号>,<行号> <file>
看这一行是哪个 commit 引入的、git show <commit> 能看到什么。如果 commit 信息量 >= 注释——注释可以删。

实验 4：搜重复短语
bash
grep -r "单写者" src/ | wc -l
grep -r "只升不降" src/ | wc -l
grep -r "静默失效" src/ | wc -l
如果同一句话在 20 个文件里出现——说明这是一个跨文件的概念，应该收敛到一份 docs，其他位置只留一行引用。

实验 5：找"孤儿注释"
搜 已删除 / 已移除 / 已废弃 / 不再：

bash
grep -rn "已删除\|已移除\|已废弃\|不再" src/
每一条都是一个"注释在代替 git 记录历史"的现场。

五、如果你要动手：建议的顺序
不建议一上来就大删。推荐这样一个渐进流程：

第 1 步：建 docs 目录（半天）
在 repo 根部建：

text
docs/
  design/
    jit-warmup.md            # JitWarmup / 叶子契约 / MustWarmLeaves
    cross-mod-compat.md      # XIAOWO / Wage / RealPrinter 避让哲学
    crash-defense.md         # 0x80131506 / CrashProbe / 预热体系
    cfg-migration.md         # 迁移链 + 终止线
    silent-failure.md        # "绝不静默失效"的判据
    monotonic-clock.md       # PollThrottle 的存在理由
    readme.md                # 索引
先写 docs，别急着删。 让 docs 成为注释的"迁入地"。

第 2 步：迁一条，验一条（每天一条）
选一个主题（比如"单调钟"），把所有相关注释复制到 docs/design/monotonic-clock.md，然后在代码里改为一行引用：

csharp
// 见 docs/design/monotonic-clock.md
Commit。这一步很重要——让 git 记录"从注释迁到 docs"这个动作本身。

第 3 步：按主题分批 commit
text
commit: docs: 收录单调钟设计（从 PollThrottle / SaveSlotScope 等迁出）
commit: refactor: PollThrottle 注释精简为一行 docs 链接
commit: docs: 收录跨 mod 兼容哲学
commit: refactor: Skip* 系列注释精简
每批一个主题，不要一次性大改动。这样出问题容易回退。

第 4 步：删历史注释（勇敢一点）
到这一步，剩下的"纯历史"注释就可以整段删了。记得先 git log -S 验证：被删的内容确实在 git 历史里。

第 5 步：跑回归
regress.ps1 跑一遍（如果可用），确认：

[REG] 标记数量没变

关键功能（升级、分页、避让）依然工作

门禁脚本 check-forbidden.ps1 通过

六、给自己设的约束（很重要）
如果你只记住一句话，就记住这句：

新决策要写进 commit message，不是写回代码注释。

否则半年后你又回到现在这个状态。写 commit 时可以问自己：

我这次改动的"为什么"是什么？

如果一年后有人 git blame 这行代码，他会想知道什么？

那段"为什么"如果能写进 commit——就不要再写回代码

唯一例外：不变量（"这段代码不能改成 X"）+ 外部契约（"这个 key 是给别的 mod 读的"）。

七、自我校验：怎么知道你做对了
做完之后，做这几个测试：

测试 1：新人视角
假装你是个从没看过这个项目的人，读一遍 DiyUpgradeMod.Upgrade.cs。

能不能在 5 分钟内理解升级流程？

有没有"莫名其妙"的代码（解释不在这里，但又不告诉你哪里能查）？

测试 2：bug 复现视角
假设你看到一个 bug（比如"从上压网格残留"）：

从代码里能找到原因吗？

找不到的话，git log --grep "网格残留" 能找到吗？

找不到的话，docs/design/grid-fx.md 里有吗？

三个都找不到——说明删太多了。删注释是有底线的。

测试 3：门禁视角
check-forbidden.ps1 还过吗？

有没有脚本依赖注释里的特定字符串（比如 R6 检查字段名）？

测试 4：注释/代码比
随便挑三个文件：

bash
grep -c "^\s*//" <file>   # 注释行
grep -vc "^\s*//" <file>  # 非注释行
如果注释行数 >= 代码行数——说明还该继续删。

八、最后一条建议
不要追求"零注释"。

好的代码不是没有注释，而是：每一条注释都被问过"它值得存在吗"，并且回答是 yes。

你现在要做的不是"删除注释"，而是从"默认保留"切换到"默认删除，逐条抵抗"。让每一条留下来的注释都是战斗过的——它之所以在，是因为删了会出问题，不是因为它曾经被人写过。

这个心态转换做完，这个工程就回到了 mod 的本质：为功能服务，而不是为历史服务。
